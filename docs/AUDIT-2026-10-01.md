# PANINI CLI audit and roadmap: what it takes to beat Codex CLI

Date: 2026-10-01 · Scope: `src/panini_cli` (≈6,900 lines), tests (151 passing), packaging · Machine: Windows 11, Ollama with `qwen2.5:3b-instruct`.

Everything marked **verified** was reproduced on this machine during the audit. The Codex CLI comparison is based on Codex's
publicly documented features as I know them; check them against the current release before you plan around them.

---

## 1. Verdict

PANINI CLI has a solid, unusually careful core: approval-gated tools, workspace-bound paths, secret-file blocking,
diff-before-apply with stale-write detection, Job-object process trees, hash-chained receipts, trusted hooks, and now per-task
local/cloud routing. Codex CLI doesn't have that last one, and it is the clearest way to beat Codex.

It is **not yet ahead of Codex CLI**:

1. Two correctness bugs in the default Windows sandbox make the agent believe failed commands succeeded and keep it from running
   common toolchains.
2. The interaction layer (input, TUI, context management, git integration, MCP, web, images) is a generation behind.
3. Nothing measures whether a change to routing or the agent makes it better, so "more powerful than Codex" cannot be shown yet.

## 2. Verified defects (fix first)

### P0-1 · Native sandbox reports success for failed PowerShell commands — **verified**

`src/panini_cli/agent/native_sandbox.py:146-149`: the wrapper runs `& 'command.ps1' *>&1 | Out-File …` and then checks `$?`.
`$?` reflects `Out-File`, which succeeds, so any non-terminating PowerShell error exits 0.

| Command (native sandbox) | Expected | Got |
| --- | --- | --- |
| `nosuchcmd123` | 1 | **0** |
| `Get-Item nope.txt` | 1 | **0** |
| `cmd /c exit 3` | 3 | 3 |

The host-scope runner (`shell.py:47-55`) gets all of these right. Because `native` is the default sandbox on Windows, the agent
reads "Exit code: 0" for failed builds and tests and reports false success, which breaks the "never claim you verified" rule.
**Fix:** put the `$paniniOk` / `$LASTEXITCODE` epilogue from `shell_argv` at the end of `command.ps1` itself, so the script
`exit`s with the real code and `$LASTEXITCODE` carries it through the pipeline. Add a regression test with these three commands.

### P0-2 · The default sandbox cannot run common toolchains — **verified**

Inside the native sandbox, `python --version` fails ("not recognized"). User-installed toolchains under `%LOCALAPPDATA%`/the
venv are not on the sandbox's `PATH` or readable, and network is fully blocked, so `npm install` and `pip install` fail too.
The model then has to escalate to `scope=host` for ordinary test runs, which costs an approval prompt each time and removes the
sandbox from exactly the commands that need it.
**Fix:** grant read+execute on detected toolchain roots (the workspace `.venv`, `py`/`python` installs, Node, Git), resolve
them into the sandbox `PATH`, and add an opt-in per-session network allowance (Codex's `network_access` equivalent).

### P0-3 · Every sandboxed command walks the entire workspace first — **verified**

`_reject_unsafe_workspace_links` (`native_sandbox.py:36`, called at `:230`) `os.walk`s the whole tree, including
`node_modules` and `.venv`, before **every** command: 0.8 s for this 10 k-file repo, which scales linearly with repo size. It also
rejects any hard-linked file (`st_nlink > 1`). Package managers that hard-link from a global cache (pnpm, and probably uv's
default link mode) will then fail every sandboxed command.
**Fix:** cache the scan per workspace and invalidate it on change (directory mtimes), skip `SKIP_DIRS`, and allow hard links whose
other names are provably inside the workspace or a read-only cache.

### P1 bugs (smaller, verified by reading the code)

| Where | Problem | Fix |
| --- | --- | --- |
| `src/panini_cli/cli.py:17` | `os.getenv("PANINI_CLI_DATA") or os.getenv("PANINI_CLI_DATA")`: a rename left a duplicate; the old variable is no longer read | Read the legacy name or drop it |
| `agent/sessions.py:42` | Pruning keeps 50 sessions **globally**, so one busy repo deletes another repo's history | Prune per workspace |
| `agent/tools.py:284` | `search_code` re-hashes the whole file for **every matching line** | Hash once per file |
| `agent/loop.py:272` | Context fit counts characters / 4 and only drops tool **outputs**; large `write_file`/`apply_patch` arguments and assistant text are never trimmed, and the real `input_tokens` from the API is ignored | Use reported usage; add compaction (see §3.3) |
| `agent/loop.py:179` | Tool calls run strictly sequentially, even parallel read-only calls the model batched | Run consecutive read-only calls concurrently |
| `agent/cli.py` `/model` | Switching model does not reset routing state or the prompt-cache key | Reset `_routed_user` and `cache_key` |
| Repo | Two different CLIs: `run.py` → `panini_cli.cli` (managed engine) vs `panini-cli` → `panini_cli.agent.cli`. Undocumented and confusing | Merge into one command tree (`panini-cli engine …`) or document |
| Repo | Nothing committed yet; CI has never run | First commit, push, green CI |
| `config.py` defaults | Router tiers are `gpt-4.1-nano/mini/4.1`, while the code already knows newer tier names (`luna`/`terra`/`sol`/`astra`) | Make the default tiers whatever your key's current models are |

## 3. Parity: what Codex CLI has that PANINI must match

### 3.1 Approval policy that doesn't nag
- **Trusted read-only command allowlist**: `git status/diff/log/show`, `ls`/`Get-ChildItem`, `rg`, `cat`/`Get-Content`, test runners in
  read-only form. Auto-approve them in `ask` and `edits` modes. This is the biggest source of friction today, because every command asks.
- **"Approve for session"** answer (`a`) for a command prefix, e.g. always allow `pytest …` in this session.
- **On-failure mode**: run in the sandbox without asking, and ask only to retry outside it when the sandbox blocks the command.
- Persist per-project approvals in `.panini/approvals.json`, behind the same trust model as hooks.

### 3.2 A real terminal UI
- Multiline input, history (↑), Ctrl+R search, Esc to interrupt, paste detection.
- `@path` file mentions with fuzzy completion; `/` command palette.
- A streaming status line showing the model in use, tokens, **$ spent this session** and the context-window %.
- Side-by-side diff review with per-hunk accept/reject.
- Implementation: `prompt_toolkit` (fast to ship) or Textual (full-screen). Keep the plain mode for `exec` and pipes.

### 3.3 Context management
- `/compact` and **auto-compaction** at ~80 % of the window: summarize older turns into a structured note (goals, decisions,
  files touched, open issues). **Have the local model write the summary for free**, a PANINI-only advantage.
- Use real `input_tokens` from responses; show the context % in the status line.

### 3.4 Git-native workflow
- **Checkpoint per turn** using a hidden git ref (stash-like commit) so `/undo` also reverts **command** side effects on tracked files,
  not only file-tool edits.
- `/diff` (the session's changes), `/review` (review the working tree or a branch with a strong model), `/commit` (message drafted by
  the local model).
- Warn when the workspace is not a git repo or is dirty before an `auto` run.

### 3.5 MCP
- MCP **client**: load servers from `~/.panini/config.toml`, expose their tools through the same approval/receipt/hook pipeline.
- MCP **server**: `panini-cli mcp-server`, so other agents can call PANINI (its router included) as a tool.

### 3.6 Web and images
- `web_search` / `web_fetch` tools (approval-gated, receipts, prompt-injection framing as for command output).
- Image input (`--image`, paste) for screenshots of errors and UI; route these to a vision-capable cloud model only.

### 3.7 Configuration
- `~/.panini/config.toml` with **profiles** (`--profile cheap`, `--profile offline`, `--profile review`), covering model tiers, approval
  mode, sandbox, local model, MCP servers and budgets. Environment variables keep overriding.
- Hierarchical `AGENTS.md` (nearest directory wins, as Codex does), not only the root and global files.

### 3.8 Automation
- `exec --json` (JSONL events), `exec --output-schema schema.json` (the loop already supports `output_schema`; only the CLI flag
  is missing), prompt from stdin (`exec -`), `--ephemeral`, and exit codes that distinguish failure from incomplete.
- `resume --last`, `sessions --all`, and session export to Markdown.

## 4. Differentiators: where PANINI can be clearly better than Codex

These build on what PANINI already has: routing, local models, receipts, Windows focus.

1. **Cost ledger and budgets.** Price table per model; show `$` per turn and session; `--budget 0.50` stops or downgrades
   when reached; `panini-cli usage` gives weekly spend and "saved by local routing". Codex can't show savings because it doesn't route.
2. **"Local scouts, cloud surgeon."** Run read-only exploration (search, read, summarize files, find call sites) as a **sub-agent on the
   local model**, and hand the cloud model a compact brief. Cloud tokens go to edits and reasoning, not to reading files.
   This is the largest potential cost win and should be measured (§5).
3. **Learned router.** Log every route with its outcome (completed, escalated, user `/undo`, tests passed). Fit the offline estimator's weights
   (or a tiny classifier run by the local model) from this local history, so routing improves per user and per repo.
   Jev stays as the online judge; the learned prior replaces the hand-written keyword lists.
4. **Verification-first completion.** Detect the project's test/lint/type commands (`pyproject`, `package.json`, `Cargo.toml`); after
   edits, run the relevant ones in the sandbox automatically and refuse to report "done" while they fail, unless the user overrides.
   Attach the result to the receipt. "Verified" then becomes a property of every finished task, not only the banner.
5. **Small-model tooling.** Give the local tier a reduced tool set (read/list/search/edit), shorter instructions and few-shot tool-call
   examples; use Ollama's structured outputs for tool arguments; offer `qwen2.5-coder` / 7B as an automatic step up before
   escalating to the cloud ("local-strong" tier).
6. **Repo intelligence offline.** A tree-sitter symbol index plus local embeddings (Ollama `nomic-embed-text`), incrementally updated,
   powering `search_code` with symbol-aware results. Free, private, and it makes the small model far more useful.
7. **Speculative drafting.** For mid-tier tasks the local model drafts the patch and a cheap cloud model reviews and corrects it. This only
   ships if §5 shows it saves money **without** losing solves.
8. **Windows done properly.** Make the AppContainer sandbox actually usable (P0-2), add a PowerShell-aware command parser for the
   allowlist, and ship winget/Scoop packages and a signed binary. Windows has historically been Codex's weakest platform; it can be PANINI's strongest.
9. **Receipts you can hand to someone.** `panini-cli receipts export` produces a signed, human-readable report of what the agent read,
   changed, ran and verified, for PR descriptions and audits.

## 5. Measure before claiming "better than Codex"

Without measurement, none of the above can be called an improvement. Build this before §4.

- **Eval harness** (`evals/`): 30–100 real tasks (bug fixes, features, refactors, local-machine questions) with a test oracle each,
  in throwaway git worktrees. Record solved, cloud tokens, $ cost, wall time, approvals asked and escalations.
- **Paired runs**: PANINI `auto` vs PANINI `--model gpt-…` (no routing) vs Codex CLI `exec` on the same tasks. Report solve rate
  and cost-per-solve. This is the only honest proof of "more powerful".
- **Promotion gate** (as JEV-RETRIEVAL.md already proposes for search): a router or prompt change ships only if it doesn't lose
  solves and cuts cost or time.
- Run the cheap subset in CI on every PR with a scripted model, and the live subset nightly.

## 6. Engineering and release hygiene

- First commit; push; get `.github/workflows/ci.yml` green. Add `ruff` (lint+format) and `mypy --strict` for `agent/` to the CI.
- Coverage report; the new router/Ollama code is well covered, but `cli.py` (960 lines) and `server.py` are thinly tested.
- Split `agent/cli.py` (960 lines) into `ui/terminal.py`, `commands/*.py` and `session.py`.
- Packaging: PyInstaller **onedir** (or Nuitka) for a faster cold start than 1.0 s; code-sign the exe; publish to PyPI (`pipx install
  panini-cli`), winget and Scoop; add `panini-cli update`.
- Version from one place (`pyproject` and `agent/__init__.py` currently both hold it).
- `SECURITY.md` (threat model: prompt injection through files and command output, sandbox scope, hook trust) and `CONTRIBUTING.md`.
- Opt-in, local-only telemetry file feeding the learned router (§4.3). Nothing leaves the machine.

### What the evals changed

The first paired run (`evals/results/20261001-232423.md`) showed routing *losing* solves: `auto` 5/10 vs pinned
`gpt-5.6-terra` 8/10, and `qwen2.5:3b` pinned 0/10. It also exposed a harness bug (the system `python` had no pytest).
The fixes above, limiting the local tier to read-only questions and redoing untrustworthy local answers in the cloud,
came from reading those failures. The final run (`evals/results/20261002-000831.md`): `auto` 10/10 at $0.0226 per solve vs pinned `gpt-5.6-terra` 10/10 at $0.0462, about 5 s slower per task.
